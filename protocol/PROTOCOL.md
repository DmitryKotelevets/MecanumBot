# MecanumBot — протокол USB (телефон ↔ ESP32-C6)

Версия протокола (`proto_ver`): **1**. Документ: 1.0, 2026-09-26.

Этот файл — **источник истины** для обеих реализаций (firmware `lib/protocol`, android `core`). Он заменяет DESIGN.md §3; при расхождении прав этот документ. Тестовые векторы — `protocol/vectors.json`, их генерирует `protocol/gen_vectors.py` (эталонная реализация CRC, раскладок и парсера на Python). JSON вручную не править.

Порядок изменения протокола: этот файл → `gen_vectors.py` → `python3 protocol/gen_vectors.py` → обе реализации → тесты. Несовместимое изменение повышает `proto_ver`; обе стороны обновляются в одном PR.

---

## 1. Транспорт

- USB CDC-ACM через нативный USB Serial/JTAG ESP32-C6 (VID `0x303A`, PID `0x1001`). Телефон — USB-хост.
- Baud rate не важен (выставлять 115200). **DTR/RTS не трогать**: смена линий может перевести C6 в загрузчик.
- Поток байтов без собственной разметки: границы кадров восстанавливаются только по формату ниже (§3).
- После каждого сброса ESP32 USB-устройство переподключается. Это штатная ситуация: телефон переоткрывает порт и снова шлёт HELLO.

## 2. Соглашения

- Все многобайтовые числа — **little-endian**.
- `seq` — циклический счётчик u8 **каждого отправителя**, +1 на каждый отправленный кадр любого типа, после 0xFF идёт 0x00. Телефон и ESP32 ведут свои счётчики независимо. Повтор кадра (OTA_DATA после таймаута, STOP ×3) получает новый `seq`.
- Скорости — `i8` в диапазоне −127…127, это −1.0…+1.0 (`v = raw / 127`). Значение **−128 вне диапазона**: приёмник трактует его как −127. Кодек (encode/decode) возвращает сырое значение с провода; ограничение до −127 делает обработчик команды.
- Строки — UTF-8 без терминатора. `str8` = `len u8` + байты строки.
- Зарезервированные биты и значения отправитель ставит в 0, приёмник игнорирует.

### 2.1 Оси и знаки движения
Система координат робота, вид сверху:

| Величина | +1.0 | Геймпад (DESIGN §5.6) |
|---|---|---|
| `vy` | вперёд | `−AXIS_Y` левого стика |
| `vx` | вправо (боком) | `AXIS_X` левого стика |
| `w` | разворот по часовой стрелке | X правого стика (`AXIS_Z` или `AXIS_RX`) |

Кинематика (DESIGN §4.4) при этих знаках: `FL = vy + vx + w`, `FR = vy − vx − w`, `RL = vy − vx + w`, `RR = vy + vx − w`. Проверка: `vx=+1` → FL+, FR−, RL−, RR+ (едет вправо); `w=+1` → левые колёса вперёд, правые назад (по часовой). Положительная скорость колеса = колесо катит робота вперёд (после применения `invert`/`map` калибровки).

## 3. Кадр

```
+------+------+-----+-----+----------------+------+
| 0xAA | type | len | seq | payload[len]   | crc8 |
+------+------+-----+-----+----------------+------+
   1      1      1     1        0…200          1      = 5 + len байт
```

- `type` — тип кадра (§4). `len` — длина payload, 0…200, и она должна лежать в допустимом диапазоне для `type` (таблица §4).
- `crc8` — CRC-8/SMBUS: poly `0x07`, init `0x00`, без reflect, xorout `0x00`, по байтам `type, len, seq, payload`. Контрольное значение: CRC(`"123456789"`) = `0xF4`.

### 3.1 Приём (алгоритм, обязательный для обеих сторон)
Приёмник держит буфер на один максимальный кадр (205 байт) и в цикле:

1. Отбрасывает байты до первого `0xAA`.
2. Когда доступен `type`: тип не из общей таблицы (все типы §4.1 **и** §4.2, `types[]` в vectors.json) → **отказ**.
3. Когда доступен `len`: `len > 200` или `len` вне диапазона для `type` → **отказ**.
4. Когда доступен весь кадр (`5 + len` байт): CRC не сходится → **отказ**. Иначе кадр принят, удаляется из буфера целиком.
5. Неполный кадр ждёт следующих байт; это не ошибка.

**Отказ**: `crc_err++`, из буфера удаляется **только стартовый байт 0xAA**, сканирование продолжается со следующего байта уже накопленного буфера. Байты «отвергнутого кадра» не выбрасываются: настоящий кадр может начинаться внутри них (обрыв кадра, мусорный 0xAA, 0xAA внутри payload).

Проверка `type`/`len` на заголовке нужна, чтобы мусорный 0xAA не заставлял ждать до 200 байт (≈ 0,6 с при 40 Гц DRIVE — дольше failsafe).

Рекомендуется (в векторах не моделируется): если в буфере лежит неполный кадр и 50 мс не приходило новых байт, выполнить отказ.

Парсер обеих сторон одинаков и не зависит от направления: корректный кадр «чужого» направления (например, LOG, пришедший на ESP32) парсером принимается, а обработчик его игнорирует; в `crc_err` он не считается.

Кадр, принятый парсером, но с неверным содержимым (недопустимые значения полей), парсером не отвергается — это решает обработчик типа (§5).

## 4. Типы кадров

Длина payload строго фиксирована, если min = max. Кадр другой длины отвергается парсером (§3.1).

### 4.1 Телефон → ESP32

| type | Имя | len | payload | Ответ |
|---|---|---|---|---|
| 0x00 | HELLO | 3 | `proto_ver u8, app_major u8, app_minor u8` | HELLO_ACK |
| 0x01 | DRIVE | 4 | `flags u8, vx i8, vy i8, w i8` | — |
| 0x02 | MOTOR_RAW | 4 | `m1 i8, m2 i8, m3 i8, m4 i8` | — |
| 0x03 | PING | 4 | `ts u32` | PONG |
| 0x04 | CONFIG | 22 | см. §4.4 | ACK |
| 0x05 | STOP | 0 | — | ACK |
| 0x06 | GET_CONFIG | 0 | — | CONFIG_DATA |
| 0x10 | OTA_BEGIN | 36 | `size u32, sha256 [32]` | ACK |
| 0x11 | OTA_DATA | 5…196 | `offset u32, data [1…192]` | ACK |
| 0x12 | OTA_END | 0 | — | ACK |
| 0x13 | OTA_ABORT | 0 | — | ACK |
| 0x20 | WIFI_OTA_ENTER | 2…97 | `ssid str8 (≤32 байт), pass str8 (≤63 байт)` | ACK, затем WIFI_STATUS |
| 0x21 | WIFI_OTA_EXIT | 0 | — | ACK |
| 0x7F | REBOOT | 0 | — | — |

DRIVE `flags`:

| Биты | Значение |
|---|---|
| bit0 | enable: 1 — ехать, 0 — стоять (нулевой «пульс») |
| bit1..2 | источник: 0 test, 1 local pad, 2 remote, 3 зарезервировано |
| bit3..7 | зарезервировано |

`m1…m4` в MOTOR_RAW — **физические каналы** M1–M4 (DESIGN §2.3), в обход кинематики, `map`, `invert`, `trim` и `min_duty`. Ограничение `max_duty` действует: 127 при `max_duty=80` даёт 80 % PWM.

### 4.2 ESP32 → телефон

| type | Имя | len | payload | Когда |
|---|---|---|---|---|
| 0x80 | HELLO_ACK | 6 | `proto_ver u8, fw_major u8, fw_minor u8, reset_reason u8, reset_count u16` | на HELLO и сам при подключении хоста (§5.6) |
| 0x81 | TELEMETRY | 20 | см. §4.3 | 10 Гц, всегда |
| 0x82 | ACK | 3 | `req_type u8, req_seq u8, status u8` | на CONFIG, STOP, OTA_\*, WIFI_OTA_\* |
| 0x83 | LOG | 1…200 | `level u8, text [0…199]` | по событию |
| 0x84 | PONG | 4 | `ts u32` (копия из PING) | на PING |
| 0x85 | CONFIG_DATA | 22 | как CONFIG (§4.4) | на GET_CONFIG |
| 0x86 | WIFI_STATUS | 5 | `state u8, ip [4]` | при смене состояния Wi-Fi |

ACK: `req_type` и `req_seq` — тип и `seq` подтверждаемого кадра. `status`: 0 OK, 1 ERR (недопустимое содержимое, ошибка операции), 2 BUSY (команда недоступна в текущем режиме).

LOG `level` (предложено): 0 error, 1 warn, 2 info, 3 debug.

WIFI_STATUS `state` (предложено): 0 off, 1 connecting, 2 connected (в `ip` адрес), 3 error. `ip` в порядке октетов: `192.168.1.42` → `c0 a8 01 2a`. При `state ≠ 2` — `0.0.0.0`.

HELLO_ACK: `reset_reason` — значение `esp_reset_reason()` (`esp_reset_reason_t`) как есть; `reset_count` — счётчик загрузок из NVS, +1 при каждом старте, после 65535 → 0.

### 4.3 TELEMETRY payload (20 байт)

| Смещение | Поле | Тип | Описание |
|---|---|---|---|
| 0 | `last_seq` | u8 | `seq` последнего принятого DRIVE/MOTOR_RAW |
| 1 | `flags` | u8 | см. ниже |
| 2 | `pwm[4]` | i8 ×4 | фактический выход на физические каналы M1–M4, −127…127 |
| 6 | `vm_mv` | u16 | напряжение VM, мВ |
| 8 | `crc_err` | u16 | отказы парсера с момента старта (§3.1), насыщается на 65535 |
| 10 | `rx_frames` | u16 | принято корректных кадров любого типа за последнюю секунду |
| 12 | `uptime_s` | u32 | секунды с момента старта |
| 16 | `fw_major` | u8 | |
| 17 | `fw_minor` | u8 | |
| 18 | `loop_max_us` | u16 | максимум длительности `loop()` за последнюю секунду, мкс, насыщается на 65535 |

`flags`: bit0 failsafe, bit1 fault A (nFAULT #A), bit2 fault B, bit3 raw mode, bit4 ota mode, bit5 wifi mode, bit6 enable (последний DRIVE был с enable=1 и failsafe не активен), bit7 зарезервирован.

### 4.4 CONFIG / CONFIG_DATA payload (22 байта)

| Смещение | Поле | Тип | По умолчанию | Допустимо (предложено) |
|---|---|---|---|---|
| 0 | `version` | u8 | 1 | только 1 |
| 1 | `map[4]` | u8 ×4 | 0,1,2,3 | перестановка 0…3; `map[i]` — физический канал для колеса i (FL, FR, RL, RR) |
| 5 | `invert[4]` | u8 ×4 | 0,0,0,0 | 0/1 для FL, FR, RL, RR |
| 9 | `max_duty` | u8 | 100 | 1…100, % |
| 10 | `slew_ms` | u16 | 250 | 0…2000; время разгона 0→100 % |
| 12 | `trim[4]` | u8 ×4 | 100 ×4 | 50…100, % для FL, FR, RL, RR |
| 16 | `brake` | u8 | 1 | 0 выбег, 1 торможение при STOP/failsafe |
| 17 | `min_duty` | u8 | 15 | 0…`max_duty − 1`, % |
| 18 | `failsafe_ms` | u16 | 300 | 100…1000 |
| 20 | `pwm_hz` | u16 | 20000 | 1000…30000 |

CONFIG с любым недопустимым полем не применяется и не пишется в NVS: ACK status 1 (ERR). Иначе конфигурация применяется сразу, сохраняется в NVS, ACK status 0.

## 5. Поведение ESP32

### 5.1 Режимы
| Режим | Вход | Выход |
|---|---|---|
| DRIVE (старт) | старт, STOP, DRIVE из RAW | — |
| RAW | MOTOR_RAW | DRIVE или STOP → DRIVE |
| OTA | OTA_BEGIN (ACK OK) | OTA_END (перезагрузка), OTA_ABORT, 5 с без OTA_DATA → DRIVE |
| WIFI | WIFI_OTA_ENTER (ACK OK) | WIFI_OTA_EXIT, 10 мин бездействия → DRIVE |

В OTA и WIFI моторы остановлены, nSLEEP = LOW; DRIVE и MOTOR_RAW игнорируются. CONFIG, OTA_BEGIN и WIFI_OTA_ENTER в «чужом» режиме OTA/WIFI → ACK BUSY. HELLO, PING, GET_CONFIG, STOP и REBOOT работают в любом режиме.

ESP32 **не требует** HELLO перед командами (чтобы `tools/usb_console.py` работал без рукопожатия). Проверка версии — на стороне телефона: до получения HELLO_ACK с совпавшим `proto_ver` приложение не шлёт DRIVE, MOTOR_RAW, CONFIG, OTA_\*.

### 5.2 Failsafe
- Таймер сбрасывает любой корректный DRIVE (в том числе с enable=0) или MOTOR_RAW. Другие кадры его не сбрасывают.
- Через `failsafe_ms` (по умолчанию 300 мс) без таких кадров: моторы мгновенно стоп (по `brake`, без slew), флаг failsafe в TELEMETRY.
- Выход из failsafe — следующий корректный DRIVE/MOTOR_RAW; скорость набирается от нуля с учётом slew.
- После старта прошивки failsafe активен, пока не придёт первый DRIVE/MOTOR_RAW.

### 5.3 STOP
Немедленная остановка без slew (по `brake`), команда обнуляется, режим → DRIVE, ACK OK. Движение возобновляется следующим DRIVE с enable=1. Телефон шлёт STOP три раза подряд; каждый получает свой ACK.

### 5.4 OTA по USB
1. `OTA_BEGIN(size, sha256)` → ESP32 останавливает моторы, nSLEEP LOW, `Update.begin(size)`. ACK OK или ERR (нет места, размер 0).
2. `OTA_DATA(offset, data)` stop-and-wait: телефон шлёт следующий кусок только после ACK на предыдущий, при отсутствии ACK 200 мс — повтор того же куска. ESP32: `offset` = уже принято → запись, ACK OK; `offset` = начало предыдущего куска (повтор, наш ACK потерялся) → без записи, ACK OK; иначе ACK ERR.
3. `OTA_END` → `Update.end(true)`, сверка sha256 со значением из OTA_BEGIN. Совпало: ACK OK, через 200 мс `ESP.restart()`. Не совпало или принято не `size` байт: `Update.abort()`, ACK ERR, режим DRIVE.
4. `OTA_ABORT` (ACK OK) или 5 с без OTA_DATA → `Update.abort()`, режим DRIVE.

### 5.5 Wi-Fi OTA
`WIFI_OTA_ENTER(ssid, pass)` → ACK, режим WIFI, WIFI_STATUS при каждой смене состояния. Пустые `ssid` и `pass` — взять сохранённые в NVS (`mbot/wifi`); если их нет — ACK ERR. Непустые — подключиться и при успехе сохранить. Выход: `WIFI_OTA_EXIT` (ACK OK) или 10 мин бездействия → Wi-Fi выключен, WIFI_STATUS `state=0`, режим DRIVE.

### 5.6 Отправка
- Кадр пишется в USB только если `Serial.availableForWrite() >= 5 + len`; иначе он пропускается целиком, `loop()` не блокируется. Приоритет при нехватке места: ACK/HELLO_ACK/PONG > TELEMETRY > LOG.
- Прошивка сама отправляет HELLO_ACK, когда хост подключается к порту (после старта и после каждого переподключения USB): до этого кадр доставить нельзя. HELLO_ACK без запроса означает «ESP32 перезагрузился или порт переоткрыт»; перезагрузку телефон отличает по росту `reset_count` (или сбросу `uptime_s` в TELEMETRY).

## 6. Поведение телефона

- После открытия порта — HELLO. Несовпадение `proto_ver` в HELLO_ACK: команды не отправлять, показать «обновите прошивку/приложение».
- DRIVE шлётся 40 Гц всегда, пока порт открыт и версия совпала; без активных источников — DRIVE с нулями и enable=0.
- Очередь записи с приоритетом: STOP > DRIVE/MOTOR_RAW > остальное. Если порт не готов, DRIVE отбрасывается, а не копится.
- PING раз в секунду, RTT по PONG.
- `last_seq` в TELEMETRY показывает, какой DRIVE ESP32 принял последним; потери оцениваются сравнением `rx_frames` с числом отправленных кадров за секунду.

## 8. Тестовые векторы (`vectors.json`)

- `crc8.vectors[]` — `data_hex` → `crc`.
- `types[]` — таблица типов с `min_len`/`max_len` для проверки заголовка.
- `frames[]` — по одному и более кадру на каждый тип (обоих направлений: парсер общий, §3.1): `fields` (именованные значения, массивы для `[4]`, hex-строки для `sha256`/`data`), `payload_hex`, `frame_hex`. Тест: кодирование `fields` → `frame_hex` и декодирование `frame_hex` → `fields`.
- Имена полей в `fields` канонические, как их выдаёт `gen_vectors.py` (например, MOTOR_RAW — массив `m[4]`, а не `m1…m4`).
- `streams[]` — поток байтов по кускам `chunks` (каждый кусок — отдельный вызов `feed`); после всех кусков должно получиться ровно `expected_frames` и `expected_crc_err`.

Firmware (`pio test -e native`) и Android (`./gradlew :core:test`) читают этот файл из `protocol/`, копий не держат.

## 9. Открытые вопросы

Решения ниже приняты в этом документе как предложения по умолчанию, их стоит подтвердить:

1. **Проверка `type`/`len` на заголовке.** Неизвестный `type` — отказ, а не игнор. Плюс: мусорный 0xAA не блокирует приём до 0,6 с. Минус: старое устройство не может молча пропустить кадр нового типа, поэтому любой новый тип требует повышения `proto_ver`.
2. **`crc_err` считает все отказы парсера** (CRC, неизвестный тип, неверный `len`), а не только CRC. Поле не переименовано, чтобы не расходиться с DESIGN.md.
3. **Диапазоны CONFIG** (§4.4): `pwm_hz` 1000…30000, `failsafe_ms` 100…1000, `slew_ms` ≤ 2000 выбраны без измерений.
4. **Коды LOG `level` и WIFI_STATUS `state`** — в DESIGN.md не определены, значения предложены здесь.
5. **ACK на REBOOT** не отправляется (как в DESIGN.md). Можно добавить ACK OK перед перезагрузкой для симметрии с OTA_END.
6. **Выход из failsafe** по любому DRIVE, даже если стик уже отклонён; защищает только slew. Альтернатива: требовать DRIVE с enable=0 перед движением.
7. **`last_seq` для учёта потерь** (DESIGN §5.5) неточен: `seq` общий для всех типов, а TELEMETRY идёт реже DRIVE. Основной показатель — `rx_frames`.
8. **Failsafe активен сразу после старта** (§5.2), до первого DRIVE/MOTOR_RAW: в TELEMETRY bit0 = 1. В DESIGN.md не оговорено.
9. **Место векторов**: DESIGN §4.9 говорит `firmware/test/vectors.json`, §8 — `protocol/vectors.json`. Выбран `protocol/`.
