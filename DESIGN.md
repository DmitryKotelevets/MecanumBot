# MecanumBot — дизайн проекта

Мобильная платформа на четырёх меканум-колёсах. Мозг — Android-телефон, закреплённый на роботе. Исполнитель — ESP32-C6, подключённый к телефону по USB. Оператор управляет из браузера (позже — из приложения) и видит видео с камеры телефона. PS-джойстик подключается по Bluetooth к телефону робота или к устройству оператора.

Версия документа: 1.2, 2026-09-26. Статус: утверждённый дизайн, разработка не начата.

---

## 1. Цели и границы

### 1.1 Цели MVP
- Робот ездет во всех направлениях (вперёд/назад, вбок, разворот, диагональ) по командам с телефона.
- Управление с экрана «Тест» в приложении робота: стики, отдельные моторы, готовые манёвры.
- PS-джойстик, подключённый к телефону робота.
- Пульт в браузере оператора: экранные стики, видео MJPEG, телеметрия.
- Трёхуровневый failsafe (пульт → приложение → ESP32).
- Обновление прошивки ESP32 без отключения кабеля (OTA по USB из приложения).

### 1.2 За рамками MVP (следующие этапы)
- WebRTC-видео с низкой задержкой.
- Приложение оператора (Android/iOS) с поддержкой джойстика.
- Удержание курса по гироскопу телефона (замкнутый контур в приложении; отдельный IMU на ESP32 не нужен).
- Wi-Fi OTA с Mac по команде (для разработки прошивки).
- Автономные режимы.

### 1.3 Ключевые решения (зафиксированы)
| Решение | Выбор | Причина |
|---|---|---|
| Контроллер | ESP32-C6 | Уже есть, достаточно PWM/GPIO |
| Фреймворк прошивки | PlatformIO + Arduino core 3.x (платформа pioarduino) | Знакомый стек, C6 поддерживается только ядром 3.x |
| Телефон робота | Android | USB-связь из приложения есть только на Android |
| Канал телефон → ESP32 | USB CDC (нативный USB Serial/JTAG) | Надёжно, минимальная задержка, питание ESP32 в том же кабеле |
| Питание моторов | 5 В от телефона (OTG) → buck 3,6 В → VM DRV8833 | Моторы ~100 мА при 3,3 В, 4 шт. укладываются в OTG; нет отдельного аккумулятора и зарядки, робот легче. Запасной вариант: 1S 18650 |
| Питание ESP32 | 5 В от телефона по USB | Просто, ESP32 без Wi-Fi ≈ 100 мА |
| Драйверы | 2 × DRV8833 | Уже есть, 1,5 А на канал |
| Видео MVP | MJPEG по HTTP | Десятки строк кода, работает в любом браузере |
| Пульт MVP | Веб-страница, которую раздаёт приложение робота | Нет отдельного сервера, работает с любого устройства |

## 2. Аппаратная часть

### 2.1 Компоненты
- ESP32-C6-DevKitC-1 (или аналог с нативным USB-разъёмом).
- 2 × модуль DRV8833 (двухканальный H-мост, VM 2,7–10,8 В, до 1,5 А/канал).
- 4 × DC-мотор-редуктор из игрушечной машинки с аккумулятором 3,3 В (номинал ~3–3,7 В, малый момент — см. §11).
- 4 × меканум-колесо (2 левых + 2 правых, ролики под 45°).
- Buck-преобразователь 5 → 3,6 В, 2 А (например, регулируемый модуль на MP1584) — питание моторов.
- Буферные конденсаторы: 1000 мкФ на входе buck (шина 5 В), 470–1000 мкФ на его выходе (VM).
- Резисторный делитель для измерения VM (100 кОм / 100 кОм → ≤ 2,5 В на АЦП при 5 В) — просадка VM показывает перегрузку моторов.
- USB-C тестер тока (для настройки: измерить лимит OTG у Pixel 9a и реальные пики).
- Резисторы 10 кОм на GND на всех восьми IN драйверов и на nSLEEP: моторы не дёргаются при сбросе, загрузке и прошивке ESP32 (пины в это время в высокоомном состоянии).
- Физический выключатель в разрыв VM (после buck): аварийный стоп, независимый от электроники и софта.
- Короткий угловой USB-C кабель телефон ↔ ESP32 с фиксацией к корпусу (нагрузка не должна идти на разъём Pixel).
- Запасной вариант (если телефон отключает порт на пиках): один 18650 с платой защиты, модуль зарядки TP4056, выключатель — вместо buck.
- Конденсаторы: 100 нФ керамика на выводы каждого мотора; 220–470 мкФ электролит на VM каждого DRV8833.
- USB-C OTG-кабель телефон ↔ ESP32 (data + power).
- Телефон робота: Google Pixel 9a (Android 15+, USB-C 2.0 с OTG и PD, Bluetooth 5.3, камеры 48 МП + 13 МП сверхширокая, 5100 мА·ч, 154,7 × 73,3 × 8,9 мм, 186 г).
- Корпус, напечатанный на 3D-принтере (см. §9).

### 2.2 Питание
```
Телефон (USB OTG, 5 В) ─┬── USB ESP32-C6 → 3,3 В на плате
                        └── 1000 мкФ ── buck 5 → 3,6 В ──┬── VM DRV8833 #A
                                          470–1000 мкФ   ├── VM DRV8833 #B
                                                         └── делитель → GPIO1 (АЦП)
GND: общая для телефона (через USB), ESP32, buck и обоих DRV8833.
5 В берётся с пина 5V/VBUS платы ESP32 (он соединён с VBUS разъёма USB).
```
Правила:
- Единственный источник питания — VBUS телефона. Никаких других источников на шину 5 В.
- Бюджет тока: средний ~0,4 А на 5 В (моторы ~0,3 А через buck + ESP32 ~0,1 А); лимит OTG Pixel 9a ~1 А (измерить). Пики старта и упора гасятся конденсаторами и плавным разгоном в прошивке (`slew_ms`, §3.4), поэтому лимит скорости по умолчанию 30 % пока не измерены реальные пики.
- Земли обязательно объединены.
- Провода моторов скручены и разведены подальше от USB-кабеля.
- Моторы номинально ~3–3,7 В, buck выставляется на 3,6 В, `MAX_DUTY_PCT` по умолчанию 100 %. DRV8833 отключается при VM < 2,7 В (UVLO), поэтому телеметрия предупреждает при VM ниже 3,2 В (перегрузка или отключение порта телефоном).
- Телефон в режиме хоста не заряжается: ~2 Вт нагрузки от 5100 мА·ч дают несколько часов работы.
- Запасной вариант: 1S 18650 напрямую на VM вместо buck; делитель и прошивка не меняются.
- Если моторы заменяются на 6-вольтовые (N20), нужен аккумулятор 2S (от телефона их не запитать), `MAX_DUTY_PCT` ~80 %.

### 2.3 Распиновка ESP32-C6 (предлагаемая, проверить по плате)
| Функция | GPIO | Примечание |
|---|---|---|
| M1 (FL) IN1 / IN2 | 18 / 19 | DRV8833 #A, канал A |
| M2 (FR) IN1 / IN2 | 20 / 21 | DRV8833 #A, канал B |
| M3 (RL) IN1 / IN2 | 22 / 23 | DRV8833 #B, канал A |
| M4 (RR) IN1 / IN2 | 10 / 11 | DRV8833 #B, канал B |
| nFAULT #A / #B | 2 / 3 | вход, подтяжка вверх, активный низкий |
| nSLEEP (EEP) обоих драйверов | 6 | выход, HIGH = работа; подтяжка 10 кОм на GND |
| V_M (делитель с VM) | 1 | ADC1 |
| Статусный LED | 8 | встроенный на DevKitC |
| Отладочный UART (опционально) | 16 / 17 | UART0, отдельный USB-UART адаптер |
| USB D− / D+ | 12 / 13 | нативный USB, занят кабелем к телефону |

Избегать: GPIO 4, 5, 8, 9, 15 как strapping-пины (8 допустим для LED).

Обозначения колёс: FL — переднее левое, FR — переднее правое, RL — заднее левое, RR — заднее правое. Физическое соответствие каналов и направлений задаётся калибровкой (§4.6), поэтому ошибка в проводке исправляется без перепайки.

## 3. Протокол USB (телефон ↔ ESP32)

### 3.1 Кадр
```
+------+------+-----+-----+----------------+------+
| 0xAA | type | len | seq | payload[len]   | crc8 |
+------+------+-----+-----+----------------+------+
```
- `type` — тип кадра (u8).
- `len` — длина payload (u8, 0–200).
- `seq` — счётчик отправителя (u8, циклический).
- `crc8` — CRC-8 (poly 0x07, init 0x00, без reflect) по байтам `type, len, seq, payload`.
- Приёмник ищет 0xAA, читает заголовок, payload и crc. Кадр с плохой CRC отбрасывается, счётчик `crc_err++`.
- Все многобайтовые числа — little-endian. Скорости — int8 в диапазоне −127…127 (соответствует −1.0…+1.0).

### 3.2 Кадры телефон → ESP32
| type | Имя | payload | Описание |
|---|---|---|---|
| 0x00 | HELLO | `proto_ver u8, app_major u8, app_minor u8` | Рукопожатие. ESP32 отвечает HELLO_ACK. Приложение не отправляет команды, пока версии протокола не совпали |
| 0x01 | DRIVE | `flags u8, vx i8, vy i8, w i8` | Команда движения. flags: bit0 enable, bit1..2 источник (0 test, 1 local pad, 2 remote) |
| 0x02 | MOTOR_RAW | `m1 i8, m2 i8, m3 i8, m4 i8` | Прямое задание моторов, в обход кинематики и калибровки. Только для экрана «Тест» |
| 0x03 | PING | `ts u32` | ESP32 отвечает PONG с той же меткой |
| 0x04 | CONFIG | см. §3.4 | Запись конфигурации в NVS |
| 0x05 | STOP | — | Немедленная остановка, переход в DRIVE-режим |
| 0x06 | GET_CONFIG | — | ESP32 отвечает CONFIG_DATA |
| 0x10 | OTA_BEGIN | `size u32, sha256[32]` | Начало обновления прошивки по USB |
| 0x11 | OTA_DATA | `offset u32, data[≤192]` | Кусок прошивки |
| 0x12 | OTA_END | — | Завершить, проверить хеш, перезагрузиться |
| 0x13 | OTA_ABORT | — | Прервать обновление |
| 0x20 | WIFI_OTA_ENTER | `ssid str, pass str` (обе строки с префиксом длины u8) | Включить Wi-Fi и ArduinoOTA (режим разработки) |
| 0x21 | WIFI_OTA_EXIT | — | Выключить Wi-Fi |
| 0x7F | REBOOT | — | Перезагрузка |

### 3.3 Кадры ESP32 → телефон
| type | Имя | payload | Описание |
|---|---|---|---|
| 0x80 | HELLO_ACK | `proto_ver u8, fw_major u8, fw_minor u8, reset_reason u8, reset_count u16` | Ответ на HELLO; также отправляется сам при старте прошивки |
| 0x81 | TELEMETRY | см. ниже | 10 Гц, всегда |
| 0x82 | ACK | `req_type u8, req_seq u8, status u8` | Подтверждение CONFIG, OTA_*, WIFI_OTA_*, STOP. status: 0 OK, 1 ERR, 2 BUSY |
| 0x83 | LOG | `level u8, text[...]` | Отладочные сообщения (вместо Serial.print) |
| 0x84 | PONG | `ts u32` | Ответ на PING |
| 0x85 | CONFIG_DATA | как payload CONFIG | Текущая конфигурация |
| 0x86 | WIFI_STATUS | `state u8, ip[4]` | Состояние Wi-Fi OTA-режима |

TELEMETRY payload:
```
last_seq   u8    — seq последнего принятого кадра DRIVE/MOTOR_RAW
flags      u8    — bit0 failsafe, bit1 fault A, bit2 fault B, bit3 raw mode,
                   bit4 ota mode, bit5 wifi mode, bit6 enable
pwm[4]     i8    — фактический выход на моторы, −127…127
vm_mv      u16   — напряжение VM (шина моторов), мВ
crc_err    u16   — счётчик ошибок CRC
rx_frames  u16   — принято кадров за последнюю секунду
uptime_s   u32
fw_major   u8
fw_minor   u8
loop_max_us u16  — максимальная длительность loop() за последнюю секунду (диагностика зависаний)
```

### 3.4 CONFIG payload
```
version    u8    — версия структуры (1)
map[4]     u8    — какой физический канал (0–3) соответствует FL, FR, RL, RR
invert[4]  u8    — 0/1 инверсия для FL, FR, RL, RR
max_duty   u8    — максимальный PWM в процентах (default 100; ~80 для N20 на 2S)
slew_ms    u16   — время разгона 0→100 % PWM (default 250), плавный старт для защиты OTG
trim[4]    u8    — коэффициент на колесо в процентах, 50–100 (default 100): компенсация разброса редукторов
brake      u8    — 1 = торможение (оба входа HIGH) при STOP/failsafe, 0 = выбег (default 1)
min_duty   u8    — минимальный PWM, ниже которого мотор не крутится (default 15)
failsafe_ms u16  — таймаут (default 300)
pwm_hz     u16   — частота PWM (default 20000)
```

### 3.5 Тайминги
| Параметр | Значение |
|---|---|
| Частота DRIVE от телефона | 40 Гц (25 мс) |
| Частота TELEMETRY | 10 Гц |
| Failsafe ESP32 | 300 мс без корректного DRIVE/MOTOR_RAW → стоп |
| Таймаут источника в арбитре | 300 мс |
| STOP | отправляется 3 раза подряд |

## 4. Прошивка ESP32-C6

### 4.1 Репозиторий: `firmware/`
```

├── platformio.ini
├── src/main.cpp
├── include/config.h          — пины, константы, версия
```

### 4.3 Главный цикл
```
setup():
  link.begin()            // USB CDC
  storage.load(config)    // NVS, defaults если пусто
  motors.begin(config)
  telemetry.begin()

loop():
  link.poll() → protocol.feed(bytes) → on_frame(frame)
  failsafe.tick(now)      // если истёк — motors.stop(), flag
  if (mode == DRIVE && !failsafe.active)  motors.apply(kinematics(cmd, config))
  if (mode == RAW   && !failsafe.active)  motors.apply_raw(raw_cmd)
  telemetry.tick(now)     // 10 Гц → link.send()
  wifi_ota.tick()         // только в WIFI-режиме
```
Обработка кадров: HELLO → HELLO_ACK; DRIVE и MOTOR_RAW сбрасывают таймер failsafe; STOP обнуляет всё; CONFIG пишет в NVS и отвечает ACK; OTA_* — см. §4.7. Без RTOS-задач: один цикл, без блокировок, `delay()` не использовать.

Надёжность: Task WDT на 2 с (сброс в конце каждого loop()), при старте `esp_reset_reason()` и счётчик перезагрузок из NVS уходят в HELLO_ACK. Brownout-детектор включён. При старте прошивка сама отправляет HELLO_ACK, чтобы приложение узнало о перезагрузке.

### 4.4 Кинематика (lib/kinematics)
```
FL = vy + vx + w
FR = vy - vx - w
RL = vy - vx + w
RR = vy + vx - w
m = max(1, |FL|, |FR|, |RL|, |RR|);  все делятся на m
```
Затем для каждого колеса: применить `invert[]`, переназначить по `map[]`, масштабировать в `[min_duty, max_duty]` (мёртвая зона: |v| < 0,02 → 0). Модуль моторов ограничивает скорость изменения PWM по `slew_ms` (для остановки, STOP и failsafe ограничение не применяется — стоп мгновенный).

### 4.5 Моторы (lib/motors)
- Arduino core 3.x: `ledcAttach(pin, pwm_hz, 10)`, `ledcWrite(pin, duty)`.
- У C6 всего 6 LEDC-каналов, входов 8. Схема: на мотор один PWM-канал. Вперёд: PWM на IN1, IN2 = LOW. Назад: IN1 = LOW, PWM на IN2. При смене направления `ledcDetach(старый)` → `digitalWrite(старый, LOW)` → `ledcAttach(новый)`. Смена направления происходит только при переходе знака, не каждый тик.
- Стоп: по умолчанию торможение (оба входа HIGH) для STOP и failsafe — меканум останавливается чётко; `brake=0` в CONFIG переключает на выбег (оба LOW). Пауза 2 мс между сменой режимов, чтобы не было сквозного тока.
- Trim: итоговая скорость колеса умножается на `trim[i]/100` до масштабирования в duty.
- nFAULT читается каждые 50 мс, попадает в телеметрию. При fault выход не отключать автоматически (DRV8833 сам защищается), только сообщать.
- nSLEEP: HIGH при старте, LOW в OTA-режимах.

### 4.6 Калибровка (lib/storage)
Structure `Config` из §3.4, ключ NVS `mbot/cfg`. Мастер калибровки живёт в приложении: оно посылает MOTOR_RAW на один канал, спрашивает пользователя, какое колесо крутилось и куда, затем шлёт CONFIG. Прошивка только хранит и применяет.

### 4.7 Обновление прошивки

**Основной путь — OTA по USB из приложения** (не нужен Wi-Fi, кабель уже подключён):
1. Приложение отправляет `OTA_BEGIN(size, sha256)`. ESP32: `motors.stop()`, nSLEEP LOW, `Update.begin(size)`, ACK.
2. Приложение шлёт `OTA_DATA(offset, chunk ≤192 байт)`, ждёт ACK на каждый (stop-and-wait, при таймауте 200 мс повтор). ESP32: проверяет непрерывность offset, `Update.write()`.
3. `OTA_END`: ESP32 `Update.end(true)`, сверяет sha256, ACK и `ESP.restart()` через 200 мс.
4. `OTA_ABORT` или отсутствие OTA_DATA 5 с → `Update.abort()`, возврат в DRIVE.
Скорость ~ 60–100 КБ/с, прошивка 1 МБ ≈ 15 с. Файл `.bin` приложение получает из `firmware/.pio/build/esp32c6/firmware.bin` (кладётся в assets приложения или выбирается через файловый диалог). Тот же путь используется скриптом `tools/usb_ota.py` с Mac.

**Путь для разработки — Wi-Fi OTA по команде:**
- По кадру `WIFI_OTA_ENTER(ssid, pass)`: `WiFi.begin()`, `ArduinoOTA.setHostname("mecanumbot")`, `setPassword`, `begin()`. Моторы отключены, в телеметрии bit5, IP отправляется в WIFI_STATUS.
- Цикл: `ArduinoOTA.handle()`. Обновление с Mac: `pio run -e esp32c6_ota -t upload`.
- `WIFI_OTA_EXIT` или 10 минут бездействия → `WiFi.mode(WIFI_OFF)`, обратно в DRIVE.
- SSID/пароль можно сохранить в NVS (`mbot/wifi`), тогда `WIFI_OTA_ENTER` с пустыми строками использует сохранённые.
- Разделы: стандартная таблица `default.csv` с двумя OTA-разделами (app0/app1) подходит для обоих путей.

### 4.8 USB и логи
У USB Serial/JTAG буферы по 64 байта. Если телефон не вычитывает данные, `Serial.write` блокирует цикл. Правило: отправлять только при `Serial.availableForWrite() >= размер кадра`, иначе кадр телеметрии пропускается (LOG-кадры имеют низший приоритет). После каждого сброса ESP32 USB переподключается к телефону заново — это штатная ситуация для приложения.

`Serial` занят протоколом. Логировать через `LOG`-кадры (`log_info("...")` → type 0x83) или через `Serial1` (GPIO16/17) при `-DDEBUG_UART=1`. Никаких `Serial.print` в коде.

### 4.9 Тесты (`pio test -e native`)
- protocol: кодирование/декодирование всех типов, CRC-вектора, восстановление после мусора в потоке, обрыв кадра посередине.
- kinematics: 8 базовых направлений, нормализация, применение map/invert, мёртвая зона.
- failsafe: истечение таймаута, сброс по кадру, поведение при переполнении millis.
Тестовые векторы CRC и кадров сохранять в `firmware/test/vectors.json` и использовать те же в Android-тестах.

## 5. Android-приложение робота

### 5.1 Стек
- Kotlin, minSdk 26, Jetpack Compose, Coroutines/Flow.
- USB: `com.github.mik3y:usb-serial-for-android` (CDC-ACM).
- Сервер: Ktor embedded (engine CIO) + WebSockets + ContentNegotiation (kotlinx.serialization).
- Камера: CameraX (`ImageAnalysis`, YUV → JPEG).
- QR: ZXing для показа адреса пульта.
- Датчики: `SensorManager` (гироскоп, ротационный вектор) для удержания курса; `BatteryManager` для заряда и температуры.
- Тесты: JUnit + kotlinx-coroutines-test для `core`.

### 5.2 Модули (Gradle)
```
android-app/
├── app/                — Compose UI, DI, Activity, сервис
├── core/               — чистый Kotlin: Protocol (кадры, CRC8), Command, Arbiter, TelemetryState
├── usb/                — UsbLink: поиск устройства, открытие, чтение/запись, реконнект
├── server/             — Ktor: /ws, /stream, статика пульта, телеметрия
├── camera/             — CameraX → MJPEG-энкодер
├── input/              — GamepadReader: MotionEvent/KeyEvent → Command
├── sensors/            — гироскоп телефона → поправка w (heading hold), температура, заряд
└── fake/               — FakeLink: эмулятор ESP32 по протоколу (телеметрия, ACK, PONG, HELLO_ACK) для разработки без железа
```

### 5.3 Модель команды
```kotlin
data class Command(
    val vx: Float, val vy: Float, val w: Float,   // −1..1
    val enable: Boolean,
    val source: Source                              // TEST, LOCAL_PAD, REMOTE
)
```

### 5.4 Арбитр (core)
- Тик 25 мс (40 Гц) в отдельной корутине.
- Приоритет: TEST > LOCAL_PAD > REMOTE. Источник активен, если его последнее обновление моложе 300 мс и `enable == true`.
- Переключатель режима: AUTO / LOCAL_ONLY / REMOTE_ONLY (настройка в UI).
- Если активных источников нет — отправляется DRIVE с нулями и enable=false (это «пульс» для failsafe ESP32).
- Экран «Тест» в режиме RAW шлёт MOTOR_RAW вместо DRIVE; при выходе с экрана — STOP ×3.
- При `onPause` Activity — STOP ×3 и остановка тика (звонок, уведомление, сворачивание).
- Удержание курса (опция, после MVP): при `w == 0` от источника поправка `w` считается ПИ-регулятором по угловой скорости гироскопа телефона; при ручном повороте регулятор отключается.
- Заряд телефона ниже 20 % — предупреждение, ниже 12 % — STOP и блокировка движения: некоторые телефоны отключают питание OTG-порта при низком заряде.

### 5.5 USB (usb)
- Intent-filter `USB_DEVICE_ATTACHED` + `res/xml/device_filter.xml` с VID `0x303A`, PID `0x1001` (ESP32-C6 USB Serial/JTAG).
- При открытии порта НЕ вызывать `setDTR`/`setRTS` (иначе C6 может уйти в загрузчик). Baud 115200 (для нативного CDC не важен).
- Чтение в отдельном потоке (`SerialInputOutputManager`), байты → `Protocol.feed()` → `Flow<Frame>`.
- Запись — очередь с приоритетом: STOP > DRIVE/MOTOR_RAW > остальное. Если порт не готов, кадры DRIVE отбрасываются (не копятся).
- Реконнект: подписка на `USB_DEVICE_DETACHED` / `ATTACHED`, повтор открытия раз в 1 с.
- Статистика: кадров/с, потери по разрывам `last_seq`, RTT по PING раз в секунду.
- После открытия порта — HELLO; при несовпадении `proto_ver` команды не отправляются, экран показывает «обновите прошивку/приложение». Приход HELLO_ACK без запроса = ESP32 перезагрузился (показать причину сброса).
- Интерфейс `Link` (send/receive Flow) реализуют `UsbLink` и `FakeLink`; выбор в настройках/при отсутствии устройства.

### 5.6 Геймпад (input)
- Activity получает `MotionEvent` (`SOURCE_JOYSTICK`) и `KeyEvent` от геймпада.
- Оси: `AXIS_X/AXIS_Y` — левый стик (vx, −vy), `AXIS_Z` или `AXIS_RX` — правый стик X (w). Определять, какая ось реально меняется, и показывать сырые значения на экране «Тест».
- `KEYCODE_BUTTON_L1` — «ехать» (deadman), `AXIS_RTRIGGER`/`AXIS_GAS` — лимит скорости 0,3…1,0.
- Мёртвая зона 0,08; экспонента 1,5 для плавности.
- Раскладка хранится в DataStore, чтобы поддержать разные джойстики.

### 5.7 Сервер (server)
Порт 8080, адрес показывается на главном экране текстом и QR-кодом.

- Доступ: случайный токен генерируется при первом запуске, зашивается в QR (`http://ip:8080/?t=TOKEN`) и проверяется при подключении к `/ws`; без токена — только `/api/status`.
- Сервер слушает только адрес Wi-Fi-интерфейса; сокеты привязываются к Wi-Fi через `ConnectivityManager` (`bindProcessToNetwork`), иначе Android в сети без интернета переключит трафик на мобильную сеть.
- Режим «точка доступа»: телефон раздаёт Wi-Fi (системная функция), пульт подключается напрямую — без роутера, на улице. В приложении только подсказка и показ адреса шлюза.

| Маршрут | Назначение |
|---|---|
| `GET /` | статика пульта из `assets/pilot/` |
| `GET /stream` | MJPEG (`multipart/x-mixed-replace`) |
| `GET /snapshot.jpg` | один кадр |
| `WS /ws` | команды от пульта, телеметрия и статус к пульту |
| `GET /api/status` | JSON: версия, USB, источники, IP |

Сообщения `/ws` (JSON):
```json
// пульт → робот
{"t":"drive","seq":123,"vx":0.0,"vy":0.5,"w":0.0,"en":true}
{"t":"stop"}
// робот → пульт (10 Гц)
{"t":"telemetry","vm":3.58,"pwm":[40,40,40,40],"failsafe":false,"fault":false,
 "usb":true,"active":"REMOTE","rtt_ms":4,"rx_fps":40}
{"t":"status","fw":"0.1","app":"0.1","mode":"AUTO"}
```
Пульт отправляет `drive` 40 Гц, сервер обновляет источник REMOTE в арбитре. Один активный пульт: второе подключение получает телеметрию, но команды от него игнорируются (флаг «наблюдатель»).

### 5.8 Видео (camera)
- CameraX `ImageAnalysis`, 640×480, 15–20 к/с, `STRATEGY_KEEP_ONLY_LATEST`.
- Выбор камеры в настройках: по умолчанию сверхширокоугольная (на Pixel 9a больше обзора по бокам при езде боком), запасной вариант — основная.
- Поворот кадра по ориентации крепления (телефон горизонтально) задаётся в настройках, а не автоматически по датчику.
- Перегрев: при температуре батареи > 40 °C снижать разрешение/частоту кадров, > 45 °C — останавливать видео и предупреждать оператора; температура в телеметрии `/ws`.
- YUV_420_888 → `YuvImage.compressToJpeg(quality 60)`.
- Последний JPEG в `MutableStateFlow`; `/stream` отдаёт каждый новый кадр всем подписчикам.
- Позже: замена на WebRTC, сигналинг через тот же `/ws` (`{"t":"sdp"...}`, `{"t":"ice"...}`).

### 5.9 Экраны
1. **Главный / Статус**: USB (подключено, к/с, RTT, потери), джойстик, пульт (подключён/нет), напряжение VM и заряд телефона, IP + QR, переключатель источника, большая кнопка STOP.
2. **Тест**: экранные стики, ползунок лимита скорости (сброс на 30 % при входе), кнопка «ехать» (удерживать), STOP, готовые манёвры (1 с каждый), ползунки четырёх моторов (RAW), мастер калибровки, живые значения геймпада, кнопка «Имитировать обрыв» с измерением времени до failsafe, консоль LOG/hex.
3. **Прошивка**: выбор `.bin`, прогресс OTA по USB, версия текущей прошивки, вход/выход в Wi-Fi OTA-режим (ввод SSID/пароля).
4. **Настройки**: порт сервера, качество видео, поворот камеры, раскладка геймпада, режим источника, FakeLink.
5. **Журнал**: список сессий; каждая сессия пишется в CSV (время, источник, команда, телеметрия, события USB) в `Documents/MecanumBot/` для разбора после поездки.

### 5.10 Поведение приложения
- `FLAG_KEEP_SCREEN_ON`, яркость можно снизить в настройках.
- Foreground Service держит сервер и USB, но геймпад и камера требуют Activity на переднем плане — в документации к приложению это описано как требование.
- Просить пользователя отключить оптимизацию батареи для приложения.
- Screen pinning и режим «Не беспокоить» рекомендуются: входящий звонок уводит Activity, приложение при этом отправляет STOP.
- Разрешения и манифест (Android 14–15): `CAMERA`, `INTERNET`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_CAMERA`, `POST_NOTIFICATIONS`; тип сервиса `camera|connectedDevice`; `android.hardware.usb.host` в `uses-feature`.

## 6. Пульт оператора (веб)

`pilot-web/` — статическая страница без сборщика (HTML + CSS + один JS-файл), копируется в `android-app/app/src/main/assets/pilot/`.

## 7. Failsafe — три уровня
1. **Пульт**: при закрытии WebSocket или молчании > 300 мс арбитр перестаёт учитывать REMOTE.
2. **Приложение**: без активных источников шлёт нулевой DRIVE; при `onPause`, ошибке USB или крахе — STOP ×3 (насколько успеет).
3. **ESP32**: нет корректного DRIVE/MOTOR_RAW > 300 мс → моторы стоп, флаг failsafe в телеметрии. Покрывает падение приложения и выдернутый кабель.

Дополнительно: физический выключатель VM на корпусе (нулевой уровень, работает всегда); подтяжки на входах драйверов (моторы молчат при сбросе и прошивке); кнопка «ехать» (deadman) во всех интерфейсах; лимит скорости по умолчанию 30 %; первые тесты на подставке, колёса в воздухе.

## 9. Корпус (3D-печать)
- Модули: нижняя плата с посадочными местами моторов (по форме редукторов с защёлками + винт от проворота), отсек электроники (ESP32, buck, драйверы) внизу по центру; резерв места под 18650 на случай запасного варианта, держатель телефона сверху (раздвижной, с наклоном камеры, доступ к USB-C), подставка для тестов.
- Колёсная база близка к квадратной, оси строго параллельны. Ролики образуют «X» при взгляде сверху.
- Посадка колёс: профиль выходного вала игрушечного редуктора (диаметр, D-срез, шлицы) сверить со ступицей меканум-колеса до проектирования; скорее всего, нужен печатный переходник. Проверяется на этапе 0a.
- Контакт всех четырёх колёс: жёсткое шасси на неровном полу опирается на три, и езда вбок превращается в дугу. Одна пара моторов крепится на качающейся балке (rocker) или все крепления через мягкие подушки 2–3 мм.
- Материал PETG. Резьбовые вставки M3 для разборности.
- Выключатель VM и порт USB-C кабеля выведены на корпус; кабель к телефону зафиксирован хомутом, чтобы вибрация не шла на разъём Pixel.
- Кабельный канал для USB и проводов моторов раздельно.

## 11. Открытые вопросы
- Реальный лимит OTG у Pixel 9a и пики тока моторов (этап 0a). Если порт отключается — переход на запасной вариант с 1S 18650.
- Зарядка телефона во время работы: при питании от телефона невозможна. Если понадобится, это отдельная схема с аккумулятором робота, PD-источником и хабом с pass-through.
- Хватит ли момента игрушечных моторов для платформы ~600 г на меканум-колёсах (этап 0a). Запасной вариант: мотор-редукторы N20 6 В (100–200 об/мин) с аккумулятором 2S (от телефона не запитать), `max_duty` ~80 %; электроника и протокол не меняются, меняются крепления в корпусе.
- Номиналы моторов (ток холостой и при упоре) — измерить.
- Порт платы ESP32-C6: убедиться, что используется нативный USB, а не UART-мост.
- Актуальность pioarduino vs официальная платформа PlatformIO.
- Нужен ли режим торможения (brake) для STOP или достаточно coast.

## Приложение A. CLAUDE.md (черновик)
```markdown
# MecanumBot

Проект: мобильная платформа на меканум-колёсах. Полный дизайн — DESIGN.md, протокол — protocol/PROTOCOL.md (источник истины для обеих сторон).

## Компоненты
- firmware/ — PlatformIO, ESP32-C6, Arduino core 3.x. Тесты: `cd firmware && pio test -e native`. Сборка: `pio run -e esp32c6`.
- android-app/ — Kotlin/Compose. Тесты core: `./gradlew :core:test`.
- pilot-web/ — статика, копируется в android-app/app/src/main/assets/pilot/.

## Правила
- Не использовать Serial.print в прошивке: USB занят протоколом. Логи только через LOG-кадры (log_info).
- Не вызывать delay() в loop(). Без RTOS-задач.
- Изменение протокола: сначала PROTOCOL.md и vectors.json, затем обе реализации, затем тесты.
- Любая команда движения подчиняется failsafe 300 мс. Не добавлять пути, которые могут крутить мотор без «пульса».
- В Android не трогать DTR/RTS на USB-порту.
- Модули lib/protocol, lib/kinematics, lib/failsafe и android core — без зависимостей от Arduino/Android, они должны собираться в native-тестах.
- Пины и константы только из include/config.h.
- Отправка по USB из прошивки только при Serial.availableForWrite() достаточном для кадра; никогда не блокировать loop().
- Приложение: любая работа с железом идёт через интерфейс Link; FakeLink должен поддерживать все типы кадров, чтобы UI разрабатывался без ESP32.
- STOP и failsafe всегда мгновенные, без slew; brake по умолчанию.
```
